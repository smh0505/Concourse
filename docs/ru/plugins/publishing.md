# Публикация

## Свободная установка по URL (всегда доступна)

Кто угодно может установить ваш плагин уже сегодня, без листинга где-либо, - диалог "Add Plugin"
Concourse принимает прямой URL на манифест `plugin.json`. Опубликуйте релиз GitHub со
скомпилированным `.wasm` и манифестом как ресурсами релиза, поделитесь URL ресурса релиза
манифеста - готово. Это настоящий, полноценный путь установки, а не запасной вариант - автору
плагина не нужно быть в каком-либо реестре, чтобы быть устанавливаемым.

Чтобы проверка обновлений хорошо работала для произвольного URL, публикуйте релизы обычным
способом (тегированные версии, например `v0.2.0`) и указывайте людям URL ресурса именно этого
тега, а не ссылку `.../releases/latest/...`, чтобы конкретная установка оставалась привязанной к
тому, откуда она фактически была установлена.

### Подписание кода (рекомендуется)

Если CI вашего репозитория плагина аттестует происхождение сборки для своих артефактов релиза
(например, через
[`actions/attest-build-provenance`](https://github.com/actions/attest-build-provenance)),
Concourse отображает это как рекомендательную проверку в UI подтверждения установки -
доказательство, что `.wasm`, который вот-вот установит пользователь, действительно происходит из
CI вашего собственного репозитория, а не является подделанной копией. Это не обязательно, но это
единственное, чего установка по произвольному URL иначе не может получить, в отличие от записи в
реестре (см. [Модель безопасности](./security-model)).

## Проверенный реестр

[`concourse-plugin-registry`](https://github.com/smh0505/concourse-plugin-registry) - это
курируемый вручную список с зафиксированными хэшами, который получает жёсткую проверку
содержимого на этапе установки (несовпадение отклоняется полностью, а не просто помечается) -
существенно более сильная гарантия, чем установка по произвольному URL. Честно говоря, на момент
написания он сам себя документирует как рецензированный одним человеком (`smh0505`, тем же
мейнтейнером, что и сам Concourse), а не как процесс открытой подачи заявок сообществом -
"рецензировано" означает, что кто-то действительно прочитал исходный код этой конкретной
зафиксированной версии, что не масштабируется на принятие произвольных сторонних pull request'ов
без предварительного изменения этой политики. Если вы хотите, чтобы ваш плагин рассмотрели для
включения, откройте issue в этом репозитории, а не рассчитывайте, что PR, добавляющий вашу
собственную запись, будет принят как есть.

### Что именно фиксирует запись

```json
{
  "id": "your-plugin-id",
  "name": "Your Plugin",
  "kind": "source",
  "repo": "you/your-plugin-repo",
  "manifestUrl": "https://github.com/you/your-plugin-repo/releases/download/v0.2.0/plugin.json",
  "wasmSha256": "<sha256 of the pinned .wasm, computed by the reviewer>"
}
```

`manifestUrl` всегда указывает на один конкретный, неизменяемый ресурс релиза - никогда на
`.../latest/...` - поскольку весь смысл курируемой записи в том, что устанавливаемое сегодня -
это ровно то, что было рецензировано, а не то, что вы опубликуете следующим. `wasmSha256`
вычисляется из вашего фактического артефакта релиза тем, кто его рецензирует, а затем сверяется с
реальными скачанными байтами при каждой установке через этот реестр.

### Поддержание записи актуальной

Если ваш плагин действительно попал в листинг, собственный CI реестра может автоматически
обнаруживать ваши новые релизы (через `repository_dispatch`, который отправляет ваш workflow
релиза) и открывать PR обновления версии в реестре автоматически - повторно получая, повторно
хэшируя и повторно фиксируя ресурс вашего нового релиза для рецензирования, вместо того чтобы
кому-то нужно было заметить, что вы выпустили обновление. Этот PR всё равно требует ручного
слияния человеком, той же планки рецензирования, что и первоначальный листинг.
